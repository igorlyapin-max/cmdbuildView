Техническое задание
Проект: web-интерфейс просмотра структуры CMDBuild

1. Назначение

Необходимо разработать web-приложение на Python с использованием FastAPI и Jinja2 templates для просмотра метаданных установленного CMDBuild через REST API.

Приложение должно:
- выполнять авторизацию пользователя в CMDBuild;
- давать выбор языка отображения при авторизации и сохранять выбранный язык;
- получать данные строго от имени авторизованного пользователя;
- отображать доступные пользователю классы, атрибуты классов, домены, атрибуты доменов, lookup-типы и значения lookup;
- именовать объекты и стандартные поля в соответствии с выбранным языком, если такие переводы есть в CMDBuild;
- строить иерархии классов и lookup;
- давать навигацию по странице через якоря;
- скрывать и раскрывать части иерархий в правом меню.

2. Технологический стек

Backend:
- Python;
- FastAPI;
- Jinja2 templates;
- стандартные HTTP-клиенты Python для запросов к CMDBuild REST API.

Frontend:
- HTML templates;
- CSS;
- vanilla JavaScript без обязательного frontend-фреймворка.

CMDBuild:
- REST API v3;
- базовый URL по умолчанию:
  http://127.0.0.1:8090/cmdbuild/services/rest/v3

3. Авторизация

На главной странице должна быть форма авторизации:
- URL CMDBuild API;
- login;
- password;
- display language.

Поля login/password не должны быть предзаполнены значениями admin/admin.

Поле display language должно позволять выбрать язык интерфейса до выполнения авторизации.
Выбранный язык должен сохраняться в cookie и применяться ко всем последующим запросам пользователя.

Авторизация выполняется запросом:
POST /sessions?scope=service&returnId=true

Тело запроса:
{
  "username": "...",
  "password": "..."
}

После успешной авторизации приложение получает token:
data._id

Token хранится в httpOnly cookie:
- cmdbuild_token;
- cmdbuild_base_url;
- cmdbuild_username;
- cmdbuild_language.

Все последующие запросы к CMDBuild должны выполняться с HTTP header:
CMDBuild-Authorization: <token>

Если выбран язык, все последующие запросы к CMDBuild должны также выполнять HTTP header:
Accept-Language: <language>

Данные должны быть динамическими:
- список классов;
- атрибуты;
- домены;
- lookup;
- значения lookup;
- доступность объектов.

Все это должно зависеть от прав текущего пользователя CMDBuild.

4. Локализация и источники наименований

Приложение должно использовать выбранный при логине язык для отображения наименований объектов CMDBuild.

Основные источники локализации:
- REST API CMDBuild с HTTP header Accept-Language;
- поля _description_translation, _descriptionDirect_translation, _descriptionInverse_translation, если CMDBuild их возвращает;
- endpoint переводов CMDBuild:
  GET /translations?scope=service&limit=100000
- UI locale-файлы CMDBuild:
  /cmdbuild/ui/app/locales/{language}/Locales.js
  /cmdbuild/ui/app/locales/{language}/LocalesAdministration.js

Правила выбора наименований:
- для классов использовать перевод class.<className>.description, затем _description_translation, затем description, затем name;
- для доменов использовать перевод domain.<domainName>.description, затем _description_translation, затем description, затем name;
- для descriptionDirect/descriptionInverse использовать соответствующие переводы domain.<domainName>.descriptionDirect и domain.<domainName>.descriptionInverse, затем поля REST API;
- для lookup-типов использовать перевод lookup.<lookupName>.description, затем description, затем name;
- для значений lookup использовать перевод lookup.<lookupName>.<code>.description, затем _description_translation, затем description, затем code/id;
- для атрибутов классов и доменов использовать переводы attribute/domain/class, затем _description_translation/description, затем name.

Если REST API возвращает для стандартных полей технические английские значения вроде Name, Code, Description, Type, Note, Active, Value, то они должны дополнительно переводиться через UI locale-файлы CMDBuild.

Заголовки таблиц и стандартные подписи колонок должны браться из UI locale-файлов CMDBuild:
- name;
- type;
- description;
- help/helptext;
- domain;
- source/origin;
- destination;
- cardinality;
- direct;
- inverse;
- active;
- value;
- code;
- note;
- attributes.

Если перевод в CMDBuild отсутствует, допускается fallback на английский текст приложения.

При объединении UI locale-файлов основная локаль Locales.js имеет приоритет над LocalesAdministration.js. Из административной локали следует добавлять только отсутствующие ключи, чтобы не заменять нормальные пользовательские подписи падежными административными формами.

Технические имена объектов могут показываться как code только там, где это нужно для идентификации, но техническое имя атрибута не должно дублироваться рядом с переведенным названием поля.

5. Получение классов

Классы запрашиваются через:
GET /classes?scope=service&limit=500

Для каждого класса должны использоваться поля:
- name;
- description;
- parent;
- prototype;
- active.

Классы должны сортироваться по иерархии наследования:
- сначала родитель;
- затем потомки;
- внутри одного уровня сортировка по description или name по алфавиту.

Для каждого класса строится якорь:
class-<name>

Пример:
class-Asset

Если класс является суперклассом, он должен быть помечен визуально:
- серым цветом;
- бейджем "Superclass" или локализованной подписью, если она задана.

Если у класса есть родитель, в заголовке класса должна быть ссылка на родительский класс.

6. Атрибуты классов

Атрибуты класса запрашиваются через:
GET /classes/{className}/attributes?scope=service&limit=500

Для каждого атрибута должны использоваться поля:
- name;
- type;
- description;
- _description_translation;
- inherited;
- lookupType;
- help;
- mode.

Системные атрибуты скрываются.

Системными считаются:
- Id;
- IdClass;
- IdTenant;
- mode = syshidden;
- mode = sysreadonly.

В таблице атрибутов класса должны быть колонки:
- name;
- type;
- description;
- help/helptext.

Фактические заголовки колонок должны отображаться на выбранном языке через механизм локализации из раздела 4.

Собственные атрибуты показываются в основной таблице.

Унаследованные атрибуты:
- должны располагаться перед собственными атрибутами;
- должны быть скрыты под раскрывающимся блоком с плюсиком;
- при раскрытии показываются в отдельной таблице;
- должны быть помечены как inherited или локализованной подписью, если она задана.

Для атрибутов типа lookup:
- имя атрибута должно быть ссылкой на соответствующую таблицу lookup ниже;
- рядом/ниже должно выводиться имя lookupType;
- якорь lookup строится как lookup-<lookupType>.

7. Домены под каждым классом

Под таблицами атрибутов каждого класса необходимо выводить отдельную таблицу "Домены класса", если хотя бы один домен ссылается на данный класс.

Домен считается связанным с классом, если класс входит:
- в source;
- в destination;
- в sources;
- в destinations.

Таблица "Домены класса" должна содержать колонки:
- domain;
- origin/source;
- destination;
- cardinality;
- attributes.

Фактические заголовки колонок должны отображаться на выбранном языке через механизм локализации из раздела 4.

Требования к ссылкам:
- Domain должен ссылаться на строку этого домена в полной таблице Domains;
- Origin должен содержать ссылки на соответствующие классы;
- Destination должен содержать ссылки на соответствующие классы;
- если у домена есть атрибуты, колонка "Атрибуты" должна быть ссылкой на строку атрибутов домена в полной таблице Domains;
- если у домена нет атрибутов, ссылка не создается, вместо нее выводится текст "Нет атрибутов".

8. Получение доменов

Список доменов запрашивается через:
GET /domains?scope=service&limit=1000

Для получения полного описания каждого домена дополнительно выполняется:
GET /domains/{domainName}?scope=service

Для каждого домена должны использоваться поля:
- name;
- description;
- source;
- sources;
- destination;
- destinations;
- cardinality;
- descriptionDirect;
- _descriptionDirect_translation;
- descriptionInverse;
- _descriptionInverse_translation;
- isMasterDetail;
- active.

Якорь домена:
domain-<domainName>

Якорь строки атрибутов домена:
domain-<domainName>-attributes

9. Атрибуты доменов

Атрибуты домена запрашиваются через:
GET /domains/{domainName}/attributes?scope=service&limit=1000

Для атрибутов доменов применяется та же нормализация, что и для атрибутов классов:
- name;
- type;
- description;
- _description_translation;
- help;
- lookupType;
- inherited.

Системные атрибуты скрываются по тем же правилам.

В полной таблице Domains после каждой строки домена должна быть отдельная строка с атрибутами этого домена.

Если у домена есть атрибуты, выводится таблица:
- name;
- type;
- description;
- help/helptext.

Фактические заголовки колонок должны отображаться на выбранном языке через механизм локализации из раздела 4.

Если атрибут домена имеет type = lookup:
- имя атрибута должно быть ссылкой на соответствующий lookup;
- рядом/ниже выводится lookupType.

Если атрибутов нет, выводится текст:
Атрибутов домена нет.

10. Полная таблица Domains

После всех таблиц классов должна располагаться секция:
Domains

Таблица Domains должна содержать колонки:
- domain;
- description;
- origin/source;
- destination;
- cardinality;
- direct;
- inverse;
- active.

Фактические заголовки колонок должны отображаться на выбранном языке через механизм локализации из раздела 4.

Origin и Destination должны быть ссылками на описания соответствующих классов.

Если CMDBuild возвращает массивы sources/destinations, то в ячейках должны выводиться все классы из массивов, каждый как отдельная ссылка.

11. Получение lookup-типов

Список lookup-типов запрашивается через:
GET /lookup_types?scope=service&limit=1000

Lookup должны выводиться все, а не только используемые в атрибутах.

Для lookup-типа используются поля:
- name;
- _id;
- description;
- parent;
- speciality;
- accessType.

Lookup-типы сортируются по иерархии:
- сначала родительский lookup;
- затем дочерние lookup;
- внутри одного уровня сортировка по description или name по алфавиту.

Пример:
- AAtestI llist lookup;
- Atest list;
- Atest list2.

Якорь lookup:
lookup-<lookupName>

12. Значения lookup

Значения lookup запрашиваются через:
GET /lookup_types/{lookupName}/values?scope=service&limit=1000

Имя lookupName должно URL-encode'иться, так как может содержать пробелы.

Для значения lookup используются поля:
- _id;
- code;
- description;
- _description_translation;
- parent;
- parent_id;
- active;
- index;
- note.

В таблице значений lookup должны быть колонки:
- value;
- code;
- note;
- active.

Фактические заголовки колонок должны отображаться на выбранном языке через механизм локализации из раздела 4.

Колонку parent id выводить не нужно.

Значения lookup должны сортироваться как дерево:
- сначала родитель;
- затем потомки;
- внутри одного уровня сортировка по description, затем code по алфавиту.

Иерархические lookup должны отображаться статической иерархией:
- отступами;
- без обязательного интерактивного раскрытия значений.

Если у lookup нет классов-использователей, выводится:
Классами не используется.

Если lookup используется классами, выводится список классов со ссылками на соответствующие классы и именами атрибутов, где lookup используется.

13. Правая навигационная панель

Справа должна быть фиксированная панель навигации.

В верхней части панели должны быть ссылки:
- Classes;
- Lookups;
- Domains.

Ниже должны быть три списка:
- Classes;
- Lookups;
- Domains.

Заголовок каждого списка должен содержать плюс/минус:
- "-" означает, что список раскрыт;
- "+" означает, что список скрыт.

При клике на плюс/минус заголовка:
- скрываются или показываются строки соответствующего списка в правом меню;
- сами основные объекты на странице при этом не обязаны скрываться.

В списке Classes:
- элементы сортируются по иерархии наследования;
- каждый элемент является ссылкой на блок класса;
- у элементов, имеющих потомков, есть плюс/минус для скрытия подуровней;
- при скрытии ветки должны скрываться строки потомков в меню и соответствующие блоки классов на странице.

В списке Lookups:
- элементы сортируются по иерархии parent lookup;
- каждый элемент является ссылкой на таблицу lookup;
- у элементов, имеющих потомков, есть плюс/минус для скрытия подуровней;
- при скрытии ветки должны скрываться строки потомков в меню и соответствующие блоки lookup на странице.

В списке Domains:
- элементы выводятся списком;
- каждый элемент является ссылкой на строку домена в полной таблице Domains;
- отдельная иерархия доменов не требуется.

Кнопка "Все":
- раскрывает все ветки Classes;
- раскрывает все ветки Lookups;
- раскрывает все списки Classes/Lookups/Domains;
- обновляет счетчик видимых классов.

14. JavaScript-механика отображения

Элементы дерева должны связываться через data-атрибуты:
- data-tree-row;
- data-tree-panel;
- data-tree-name;
- data-tree-parent;
- data-tree-toggle;
- data-sidebar-section;
- data-section-toggle.

Для скрытия использовать CSS-класс:
is-tree-hidden

Для скрытия секции правого меню использовать CSS-класс:
is-section-hidden

Скрытие должно работать надежно даже если у элемента задан display:flex или display:table-row.

Для этого классы скрытия должны иметь:
display: none !important;

15. API frontend

Frontend должен иметь JSON endpoint:
GET /api/classes

Если пользователь не авторизован, возвращается:
HTTP 401
{
  "success": false,
  "message": "not authenticated"
}

Если пользователь авторизован, возвращается:
{
  "success": true,
  "language": "...",
  "labels": {...},
  "classes": [...],
  "lookup_tables": [...],
  "domains": [...]
}

Поле language должно содержать фактически примененный язык.
Поле labels должно содержать локализованные подписи стандартных колонок и UI-меток, используемых шаблоном.

Этот endpoint используется для проверки и может использоваться внешними инструментами.

16. Ошибки и устойчивость

Если CMDBuild возвращает HTTP ошибку, приложение должно показать понятное сообщение.

Если один домен или lookup не удалось загрузить полностью:
- не нужно ломать всю страницу;
- для проблемного блока должно быть сохранено сообщение об ошибке.

Если у класса не удалось получить атрибуты:
- класс все равно должен отображаться;
- внутри блока класса должно быть сообщение об ошибке.

17. Проверка работоспособности

После изменений необходимо проверять:
- python syntax check:
  .venv/bin/python -m py_compile app.py

- авторизацию через POST /login;
- открытие /classes;
- открытие /api/classes;
- наличие в HTML ключевых элементов:
  - Classes;
  - Lookups;
  - Domains;
  - ссылки на class-*;
  - ссылки на lookup-*;
  - ссылки на domain-*.
- для русского языка после логина должны проверяться локализованные заголовки и поля:
  - Имя;
  - Тип;
  - Описание;
  - Код;
  - Значение;
  - Домен;
  - Источник/Назначения или соответствующие значения из locale-файлов CMDBuild.
- в HTML не должно оставаться английских заголовков колонок Name/Type/Description/Help text, если в выбранной локали CMDBuild есть соответствующие переводы.
- техническое имя атрибута не должно выводиться вторым текстом рядом с переведенным названием.
- страница /classes должна отдавать заголовки, запрещающие кеширование старой версии:
  Cache-Control: no-store, no-cache, must-revalidate, max-age=0
  Pragma: no-cache

18. Запуск

Frontend запускается командой:
.venv/bin/uvicorn app:app --host 0.0.0.0 --port 8000

URL frontend:
http://localhost:8000/

URL CMDBuild:
http://localhost:8090/cmdbuild
